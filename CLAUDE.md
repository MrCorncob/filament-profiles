# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

Not a software project — a collection of filament preset bundles, organized by slicer/export format, then filament vendor, then printer model, plus a small Python toolchain that derives new bundles for printers/materials a vendor is missing from an older, unbundled profile source. Currently the only slicer with real data is Bambu Studio (`.bbsflmt` files); TINMORRY and eSUN both have real vendor data, ELEGOO is still scaffolding-only. The layout and tooling are structured so further slicers (e.g. OrcaSlicer) and vendors (e.g. ELEGOO) can be added later without another reorganization — see "Slicers" and "Vendors" under Architecture. There is no build, lint, or test suite.

## Commands

```bash
# Report gaps: filament types in a vendor's delta source(s) with no bundle yet for a
# given printer, each labeled ALLOW or SKIP per the compatibility policy below
python3 src/find_missing_filaments.py                 # all printers, TINMORRY (default)
python3 src/find_missing_filaments.py --printer H2D   # one printer
python3 src/find_missing_filaments.py --vendor eSUN   # all printers, eSUN

# Generate new .bbsflmt bundles for the ALLOW-labeled gaps (never overwrites an existing bundle)
python3 src/convert_old_repo_to_printer.py --dry-run          # preview, TINMORRY
python3 src/convert_old_repo_to_printer.py                    # write, TINMORRY
python3 src/convert_old_repo_to_printer.py --printer P2S
python3 src/convert_old_repo_to_printer.py --vendor eSUN      # write, eSUN

# Regenerate REFERENCES.md's inventory table from the bundles actually on disk
python3 src/gen_inventory_table.py               # print the table
python3 src/gen_inventory_table.py --check       # exit 1 if REFERENCES.md is stale

# Regenerate the collapsible per-printer download tables in every README.*.md
python3 src/gen_readme_tables.py                 # print every language's block
python3 src/gen_readme_tables.py --write          # splice into every README
python3 src/gen_readme_tables.py --check          # exit 1 if any is stale

# Extract any plain .zip wrapping a .bbsflmt (rather than being a bundle itself) into its printer folder
python3 src/unzip_wrapper_zips.py --dry-run
python3 src/unzip_wrapper_zips.py --delete-zip

# Derive 0.2mm-nozzle bundles from the matching 0.4mm TINMORRY bundle on X2D/A1/A1mini
# (never overwrites an existing bundle; see "0.2mm-nozzle derivation" below)
python3 src/derive_nozzle_variants.py --dry-run          # preview
python3 src/derive_nozzle_variants.py                    # write
python3 src/derive_nozzle_variants.py --printer X2D
```

Run `gen_inventory_table.py` and `gen_readme_tables.py --write` together any time a bundle is added, removed, or renamed — both derive from `_filament_lib.inventory_rows()`, so they can't drift from each other, but neither is regenerated automatically. `gen_readme_tables.py`'s raw-download links are hardcoded to `GITHUB_OWNER`/`GITHUB_REPO`/`GITHUB_BRANCH` at the top of that file — update those constants (and rerun with `--write`) if the repo moves or this work lands on a different branch.

`find_missing_filaments.py` and `convert_old_repo_to_printer.py` take a `--vendor {TINMORRY,eSUN}` flag (default `TINMORRY`, i.e. `_filament_lib.VENDOR`) and read from that vendor's own local delta source(s), committed and tracked in this repo (a snapshot at the time each vendor was added, not auto-updated — see External references in REFERENCES.md to refetch a newer copy if needed):
- `reference-old-repo/` (TINMORRY): TINMORRY's older per-printer profile repo (https://github.com/TINMORRY/TINMORRY-filament-profile-for-Bambu-printers.git). Small `"inherits"`-based deltas, tagged by printer via an `"@BBL <code>"` string inside `inherits`.
- `reference-bambuprinters/` (TINMORRY): TINMORRY (Binh Duong)'s repo (https://github.com/tinmorrybinhduong/BambuPrinters) — see REFERENCES.md's External references. Many of its `*_Filament(*).json` files are complete per-printer exports with a blank `inherits`, tagged by printer via the filename instead (`*_Process(*).json` files are print/process settings and are ignored — out of scope, this repo only bundles filament presets).
- `reference-esun/` (eSUN): eSUN's own "HS Parameters for Bambu Lab" export — see REFERENCES.md's External references for the download URL and exact folder layout to recreate. Small deltas shaped like `reference-old-repo/`'s (`"inherits": "Bambu ... @BBL <code>"`), one per-printer subfolder per the zip's own printer names, `*Filament.json`/`*Process.json` pairs (only `*Filament.json` is read, same convention as above).

For TINMORRY, both sources are merged into one set of gaps by `_filament_lib.delta_entries("TINMORRY")`; for eSUN, only `esun_entries()` is used. Either way `find_gaps()` picks whichever source entry has evidence for a given printer (preferring a direct match over an arbitrary same-material entry from another printer — see `find_gaps` in `_filament_lib.py`). Shared logic (printer registry, gating policy, delta-source parsing, template selection, bundle merging) lives in `src/_filament_lib.py`.

**eSUN's base_material comes from the FILENAME, not `inherits`** (unlike TINMORRY's two sources): eSUN's deltas often inherit from a plain Bambu baseline profile (e.g. `"Bambu PETG Basic @BBL X2D..."`) even for reinforced/specialty variants like PETG-CF, so trusting `inherits` the way `old_repo_entries()` does would misclassify them as their un-reinforced base type. See `esun_base_material()`'s docstring. eSUN's own filenames are also inconsistent (typos like "PLA-Twinking"/"PLA-Twinkling" for the same product, mixed case, reversed word order like "UV rock PLA" vs "PLA-UV Rock") — reversed word order is handled for free since descriptors are compared as sets, but genuine misspellings need an explicit fix in `ESUN_TOKEN_FIXES`.

**Custom overrides**: to hand-force specific fields on a generated bundle (e.g. a real spec-sheet temperature that no delta source has), add `src/custom_overrides/<printer_dir>/<output_name>.json` (`<printer_dir>` is vendor-qualified — NOT slicer-qualified, e.g. `TINMORRY/X2D/0.4mm` or `eSUN/X2D/0.4mm` — since this mechanism lives inside the BambuStudio-only pipeline; see "Slicers" below) — a flat `{key: value}` dict, committed like the delta sources above. `convert_old_repo_to_printer.py` applies it as the last step after the template/delta merge, so it always wins; values must already be in the profile's final shape (e.g. a list with one entry per `filament_extruder_variant` for per-variant fields). See `_filament_lib.load_custom_override`'s docstring.

**Known gap in `find_gaps()`'s dedup check**: a candidate gap is treated as "already covered" if its token set is a subset OR superset of any existing bundle's token set for that printer (`combined <= tokens or tokens <= combined`), not just an exact match. This silently swallows some real, distinct products once a printer already has a same-family bundle with a *subset* of the candidate's tokens — e.g. once a printer has a bare `"eSUN PC"` bundle, a `"PC HT"` gap for that same printer is silently treated as covered (`{"pc"} <= {"pc","ht"}`) and never reported, even with real direct evidence or tier-proof to generate it. Confirmed present for TINMORRY too (not eSUN-specific), just rarely triggered there since TINMORRY's own data has fewer bare-vs-descriptor pairs per printer. Not fixed as of the eSUN cook (2026-07-10) because tightening it to exact-match reveals a large number of previously-silent gaps across TINMORRY's existing printers too (bare `PLA`/`TPU`/`ASA`/`ABS` alongside existing decorated variants) — a deliberate before/after comparison is needed before changing shared dedup semantics, not a fix folded into an unrelated task.

## Architecture

**Top-level split**: `profiles/` holds all slicer/vendor bundle data, `src/` holds the Python toolchain that generates/inspects it (`_filament_lib.py`'s `PROFILES_ROOT`, `PROFILES_DIR`, and `REPO_ROOT` constants are the roots — see "Slicers" below for how the first two differ). The tracked delta-source snapshots (`reference-old-repo/`, `reference-bambuprinters/`, `reference-esun/`) and `reports/` (generated diff reports) live at repo root alongside both.

**Repo layout**: `profiles/` holds one top-level folder per slicer/export format (currently just `BambuStudio/` — see "Slicers" below), each holding one folder per filament vendor (currently just `TINMORRY/` — see "Vendors" below), each holding one folder per printer model (`A1/0.4mm/`, `A1mini/0.4mm/`, `A2L/`, `H2C/`, `H2D/`, `H2S/`, `P1S/`, `P2S/`, `X2D/0.4mm/`) with `.bbsflmt` files for that printer's compatible filaments. A1, A1mini, and X2D also each have a `0.2mm/` sibling subfolder of derived 0.2mm-nozzle bundles — see "0.2mm-nozzle derivation" below.

**Slicers**: `src/_filament_lib.py`'s `SLICERS` list (`BambuStudio`, `OrcaSlicer`) is the registry of every slicer/export format this repo knows about; `SLICER` (currently `"BambuStudio"`) is the slicer the *existing* generation pipeline targets and produces bundles for (mirrors `VENDOR` below). Slicer is the outermost folder under `profiles/` — above vendor — because it determines the file FORMAT itself: `.bbsflmt` is Bambu Studio's own bundle structure, and a future OrcaSlicer export would need an entirely different file shape, not just a different vendor/printer subtree, so it can't be mixed in alongside vendor/printer the way those two mix with each other. OrcaSlicer is registered as scaffolding only: no OrcaSlicer export exists yet, so its folder doesn't exist on disk and nothing targets it. **Adding OrcaSlicer support once it's wanted**: add a slicer-specific generation pipeline (the current one is `.bbsflmt`-specific throughout — `build_bundle`, `merge_profile`, the zip-reading helpers — none of it generalizes to a different file format automatically), landing bundles under `profiles/OrcaSlicer/<Vendor>/<Printer>/`. `gen_inventory_table.py` and `gen_readme_tables.py --write` already scan every slicer in `SLICERS` (via `PROFILES_ROOT`, not the pipeline's `PROFILES_DIR`) and need no changes to pick up a new one, though `KNOWN_ORIGINAL_BUNDLES`/`is_original_bundle` are NOT slicer-qualified yet (see their docstring) — a second slicer with real bundles will need that added.

**Vendors**: `src/_filament_lib.py`'s `VENDORS` list (`TINMORRY`, `eSUN`, `ELEGOO`) is the registry of every vendor this repo knows about; `VENDOR` (still `"TINMORRY"`, the default) is only the vendor `target_printer_dir()`/`find_gaps()`/etc. fall back to when no `vendor` argument is passed. `find_gaps(printer_name, vendor)`, `delta_entries(vendor)`, `target_printer_dir(printer_name, vendor)`, `output_bundle_name(vendor, ...)`, and `build_bundle(..., vendor)` are all genuinely vendor-parameterized (not TINMORRY-hardcoded) — see `delta_entries()`'s per-vendor dispatch. TINMORRY draws on `reference-old-repo/` + `reference-bambuprinters/`; eSUN draws on `reference-esun/` via `esun_entries()` (its own parsing logic, since eSUN's file shape differs enough from TINMORRY's two sources -- see the eSUN-specific note above `find_missing_filaments.py`'s docs in the Commands section). ELEGOO is still registered as scaffolding only: no delta source data or parsing logic exists for it yet, so its folder doesn't exist on disk and no bundles are generated for it. **Adding ELEGOO (or any further vendor) once real data exists**: add it to `VENDORS`, add it to the two scripts' `--vendor` choices, write a vendor-specific `*_entries()` function and wire it into `delta_entries()` (the shared tier/family/template/merge/build machinery needs no changes — only entry-parsing is vendor-specific), landing bundles under `profiles/BambuStudio/<Vendor>/<Printer>/`. `gen_inventory_table.py` and `gen_readme_tables.py --write` already scan every vendor in `VENDORS` and need no changes to pick up a new one.

**eSUN's expanded material catalog**: eSUN's data introduced several filament_type values TINMORRY's data never needed: `PA6-CF`/`PA12-CF` (nylon-CF grades, `TIER_ENGINEERING_HIGH`, family `"PA"`), `ABS-CF`/`ABS-GF` (reinforced ABS, `TIER_ENGINEERING_MED`, family `"ABS-ASA-PC"`), and `PEBA`/`TPE` (flexible elastomers, `TIER_BASE`, each its own family — eSUN's own deltas inherit both from Bambu's TPU 95A system profile, so `FALLBACK_TEMPLATE` points them at TINMORRY's TPU 95A bundle too). All added to `HYPHENATED_MATERIALS` where the hyphen reads as part of the product name (PA6-CF, PA12-CF, ABS-CF, ABS-GF), matching PA-CF/PAHT-CF's existing convention. `DESCRIPTOR_CASE_OVERRIDES` also gained a regex fallback in `display_descriptor()` for Shore-hardness descriptors (`95a`→`95A`, `64d`→`64D`) — `str.capitalize()` alone doesn't uppercase a trailing letter after a leading digit.

**eSUN bundles on 4-variant printers (H2D, H2S, P2S, X2D) are mostly single-variant data wearing a 4-variant template**: eSUN's own per-printer exports for these printers almost universally only specify `nozzle_temperature`/`filament_flow_ratio`/`filament_max_volumetric_speed` for the "Direct Drive Standard" slot, leaving the other three (`"nil"`) — so those three variants keep the donor TINMORRY bundle's own values rather than an eSUN-specific one. This is `merge_profile`'s existing, correct, documented behavior for unspecified fields; it's just exercised far more heavily by eSUN's data than TINMORRY's ever was. Flagged in REFERENCES.md's inventory footnote; no per-bundle fix applied since there's no better eSUN-provided value to use.

**`.bbsflmt` format**: a zip archive containing `bundle_structure.json` (bundle id, filament name, Studio version, and a `filament_vendor[].filament_path[]` list mapping to the profile JSON(s) inside) plus one fully-flattened filament settings JSON per compatible printer under `TINMORRY/`. "Fully flattened" means every parameter (temps, cooling, flow, retraction, etc.) is a literal value — no `inherits` chain to resolve. Some bundles (e.g. TPU 95A, PETG GF/Marble/Metallic under `profiles/BambuStudio/TINMORRY/X2D/0.4mm/`) are dual-printer: `filament_path` has one entry for P2S and one for X2D — when reading these programmatically, select by filename substring (or printer code), don't assume index 0. A couple of bundles have non-ASCII filenames (a full-width comma, a backtick) that round-trip correctly as JSON text but don't byte-match the zip's cp437-stored entry name — walk `zipfile.namelist()` rather than looking up `bundle_structure.json`'s declared path directly.

**Per-extruder-variant fields**: parameters that vary by extruder (e.g. `filament_flow_ratio`, `nozzle_temperature`, `filament_max_volumetric_speed`) are arrays parallel to `filament_extruder_variant`. Bundles with 4 variants (`[Direct Drive Standard, Direct Drive High Flow, Bowden Standard, Bowden High Flow]`) consistently mirror the "Direct Drive High Flow" value into both Bowden slots — the merge logic in `_filament_lib.merge_profile` relies on and preserves this convention.

**Delta sources vs this repo's format**: `reference-old-repo/`'s profiles are small deltas (`"inherits": "Generic PC @BBL P1S"` + a handful of overridden keys) against Bambu Studio's own built-in system profiles for *other* printers — not self-contained, and can't be flattened for a printer without that printer's own system profile data (not available locally). `reference-bambuprinters/`'s `*_Filament(*).json` files are a mix of the same small-delta shape and complete per-printer exports (blank `inherits`, ~150 keys) — `_filament_lib.merge_profile` treats both shapes identically, since a delta with (nearly) every key just overwrites (nearly) everything the template would have supplied. Either way, the converter works around the non-self-contained cases by taking an existing bundle (ideally for the *same* printer, same material) as a machine-parameter template and layering the delta's material-specific tuning (flow ratio, plate temp, fan speed, max volumetric speed, retraction) on top, leaving `"nil"`/unspecified fields at the template's already-validated value.

**Template selection** (`_filament_lib.choose_template`): (1) an existing bundle for the *same printer* with the same `filament_type` — best; (2) an existing bundle for the same printer in the same **polymer family** (`_filament_lib.POLYMER_FAMILY` — PLA-ish, PETG-ish, TPU, ABS/ASA/PC, or PA-ish; deliberately finer than the compatibility tiers below, since e.g. a PLA-CF bundle is a bad temperature template for a PETG Galaxy gap even though both are "base tier"); (3) `_filament_lib.FALLBACK_TEMPLATE`, a repo-wide canonical set (mostly pointing at `profiles/BambuStudio/TINMORRY/X2D/0.4mm/`, which has the broadest coverage). Template lookups always use a bundle-list **snapshot taken before a conversion run starts writing** — never a live re-scan — so bundle N+1 in a batch can't template off bundle N that the same run just generated; everything traces back to a real, originally-existing bundle.

**Machine compatibility gating** (`_filament_lib.classify_gap`, `TIER_BASE`/`TIER_ENGINEERING_MED`/`TIER_ENGINEERING_HIGH`): the converter never invents a filament/printer pairing without evidence.
- Base materials (PLA, PETG, TPU, and CF-reinforced PLA/PETG/PET) are generated freely — safe on any Bambu machine.
- "Engineering" materials (ABS, ASA, ASA-CF, PC) require either a machine-coded old-repo delta (`"inherits": "... @BBL H2D"`) for that *exact* printer, OR that the printer already ships another engineering-tier bundle in this repo AND has `PRINTERS[...]["enclosed"] == True`. The `enclosed` flag (physical side panels/lid, not necessarily an actively heated chamber) exists because "tier-proof" alone is too coarse: the old repo has a direct, real `"Generic PC @BBL A1"` system-profile delta even though A1 is Bambu's open-frame budget printer, and that single fact doesn't imply ABS/ASA (whose fumes/warping specifically call for an enclosure) are also fine there. Direct evidence is trusted regardless of `enclosed`, since it's a real vendor-declared fact rather than our own inference — this is why A1 has a generated PC GF bundle but no ABS/ASA.
- High-temperature nylon materials (PA, PA-CF, PAHT-CF) require a machine-coded delta for that exact printer — never inferred from another material's tier-proof, since a working ABS profile doesn't prove a hotend can hit 300°C.
- Gaps that don't clear their bar are left as `SKIP (needs review)` and reported by `find_missing_filaments.py`, not silently generated. Consequently PA-CF/PAHT-CF exist only on X2D (the one printer with historical evidence for them), and no ABS/ASA exists on the open-frame A1/A1 mini/A2L (`enclosed: False` in `PRINTERS`).
- Because tier-proof depends on what's already on disk, generating bundles for a brand-new printer can unlock further gaps on a second pass (e.g. generating A1's direct-evidence PC GF, then rerunning, doesn't unlock anything further there since A1 isn't enclosed — but the same pattern on an enclosed printer like P1S generates PC GF first, then a rerun sees `engineering_capable and enclosed` and unlocks ABS/ASA/ASA-CF via tier-proof). Always rerun `find_missing_filaments.py` after a conversion pass to check for newly-unlocked gaps.

**0.2mm-nozzle derivation** (`src/derive_nozzle_variants.py`, policy in `_filament_lib.py`'s "0.2mm-nozzle derivation" section): a separate derivation axis from the machine-compatibility gating above — it repackages an *existing* 0.4mm TINMORRY bundle for a smaller nozzle rather than discovering a new material from a delta source. Grounded in BambuStudio's own official system profiles (`~/Library/Application Support/BambuStudio/system/BBL/filament/*0.2 nozzle.json` on a machine with Studio installed) rather than an invented scaling factor: comparing every 0.4mm/0.2mm pair for the same material+printer in that library showed (1) only `filament_max_volumetric_speed` and `compatible_printers` change between nozzle sizes — temps, flow ratio, etc. are copied unchanged; (2) the 0.2mm cap is an ABSOLUTE per-material constant, not a ratio of the 0.4mm value (PETG caps at `1` mm3/s at 0.2mm on both A1 and X2D even though their 0.4mm values differ, 8 vs 12); (3) Bambu never ships a 0.2mm profile for any CF/GF-reinforced, TPU/flexible, or PA/nylon material, on any printer — matches physical reality (abrasive fiber wears out a 0.2mm brass orifice; flexible filament doesn't extrude well through one). `NOZZLE_02_ALLOWED_TYPES` (`PLA`/`PETG`/`ABS`/`ASA`/`PC`) and `NOZZLE_02_EXCLUDE_TOKENS` (`cf`/`gf`, checked against the bundle's own name via `normalize()`) encode this gate — the token check matters because this repo's own `filament_type` doesn't always encode reinforcement (`TINMORRY PC GF` and `TINMORRY PETG CF PP` both carry a plain `PC`/`PETG` `filament_type`). Currently wired for TINMORRY only, on X2D/A1/A1mini (`NOZZLE_02_TARGETS`). **Folder layout**: each of these three printers now has a `0.4mm/` + `0.2mm/` subfolder pair (`PRINTERS[...]["dir"]`, e.g. `A1/0.4mm`). X2D already had this shape; A1 and A1mini were restructured from a flat layout (`TINMORRY/A1/*.bbsflmt`) into it to match, which breaks any previously-published raw-download link into their 0.4mm bundles (the regenerated links in README.md are correct going forward). `INVENTORY_FOLDERS`, `KNOWN_ORIGINAL_BUNDLES`, and `gen_readme_tables.py`'s `PRINTER_LABELS` were all updated for the new `.../0.4mm` folder paths.

Building this surfaced a pre-existing bug in `printer_code_of()`: it derived the zip-filename-matching token straight from the printer folder segment (e.g. `"A1mini"`), but Bambu's own display name — and therefore the token actually embedded in zip member filenames — is `"A1 mini"` with a space, so `load_bundle_profile`/`choose_template`/`printer_filament_types` silently never matched any of A1 mini's own bundles. Fixed via `PRINTER_CODE_OVERRIDES`. This also means `choose_template` can now find same-printer A1 mini templates it silently couldn't before (previously always fell through to the `FALLBACK_TEMPLATE`); existing A1 mini bundles are unaffected since nothing regenerates a bundle that already exists.

One known data quirk baked into `_filament_lib.py`: `reference-old-repo/PET-CF (X1 X1C P1S P1P).json` has a typo'd `"inherits": "Generic ABS"` even though its filename/content are unambiguously PET-CF — `FILE_BASE_MATERIAL_OVERRIDE` corrects this rather than trusting the source label.

**Generated vs original bundles**: `_filament_lib.is_original_bundle(folder, filament_name)` (`folder` is the vendor-qualified path, e.g. `TINMORRY/A1`) checks an explicit allowlist, `KNOWN_ORIGINAL_BUNDLES` — there's no reliable in-band signal on disk (a generated `bundle_id` looks like any other), so this list is maintained by hand and must be extended whenever a genuinely new original TINMORRY export is added. `gen_inventory_table.py` (REFERENCES.md, trailing `*` on the filename) and `gen_readme_tables.py` (every `README.*.md`, an "Original"/"Derived"-equivalent column per language) both derive from the same `_filament_lib.inventory_rows()`, so they can't disagree with each other — but forgetting to extend `KNOWN_ORIGINAL_BUNDLES` would make a real export show up mislabeled as "Derived" everywhere at once. The X2D PA-CF/PAHT-CF bundles in particular inherited PETG CF's nozzle/bed temperatures (no override existed in their source delta) rather than their real higher-temperature requirements — flag this if touching those two bundles.

**README.md / README.vi.md / README.zh.md structure**: three parallel translations (English, Vietnamese, Chinese), each linking to the other two at the top. All three start with a fork-provenance line, then a **⚠️ Caution** section (non-technical warning about Derived profiles, not to be confused with the machine-compatibility gating policy above — the caution is aimed at end users, the gating policy at this tooling), then the "Available profiles" section, which is entirely generated content between `<!-- BEGIN/END GENERATED PROFILE TABLES -->` markers — don't hand-edit inside those markers, they're overwritten by `gen_readme_tables.py --write`. Adding a fourth language: add a file + headers + labels entry to `LANGS` in `gen_readme_tables.py`, create the new `README.<lang>.md` with the same prose sections translated (and the markers in place), and add its link to the language switcher at the top of the other README files.

See `README.md` for the full profile inventory table and installation steps, and `REFERENCES.md` for the complete per-bundle metadata inventory and external references.
